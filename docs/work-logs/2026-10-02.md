## Issue #58: DB 側のタイムアウト（statement / lock / idle in transaction）をプールの設定に足した
- 理由: 2026-10-01 の調査で、DB 側のタイムアウトが無く、遅い文・ロック待ち・開いたままのトランザクションがプールの接続（1 インスタンス 3 本）を握り続けると分かった。daiki が Issue #58 で進めることを了承（プール数は固定のままにする判断も同日）。
- 根拠: pg 8.23.0 は Pool の設定の `statement_timeout` / `lock_timeout` / `idle_in_transaction_session_timeout` を接続の起動パラメータで送り、偽の値（0）は送らない（`node_modules/.pnpm/pg@8.23.0/node_modules/pg/lib/client.js` の getStartupConf、`connection-parameters.js`）。実 Postgres で `current_setting` が 2s / 500ms / 4s になること、100ms の statement_timeout で `pg_sleep(2)` が 57014 になることをテストで確認。値: API（Cloud Run の service・.env.example）は 10 秒 / 3 秒 / 30 秒、migrate job（backfill も流す）は文とロック待ちを 0（送らない）、idle は 30 秒。
- 判断: 必須の環境変数にした（env.ts の「アプリの設定は必須で既定値を持たない」に合わせる）。job を 0 にしたのは、backfill の 1 ファイルが表全体を 1 文で書き換え、アプリの行ロックを待つことがあるため（上限はジョブの timeout 600s）。逆向き（backfill のロック中に API が 3 秒で 55P03）は限界として run.tf に書いた。reviewer の指摘（「0 は無効」→「0 は送らず DB の既定に従う」）を反映。採用しなかった案: コードに定数で置く（env.ts の方針に反する）、query_timeout（クライアント側で待つのをやめるだけで、DB の文は動き続ける）。
- 未確認: `terraform fmt`（環境に terraform が無い。CI でも検査していない）。Cloud Run での実動作（本番・stg がまだ無い）。
- 機械化: 縛れる（env.test.ts が必須・0 以上を、database.test.ts が実 Postgres のセッションの設定と打ち切りを固定する）。
