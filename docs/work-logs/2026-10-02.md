## migrate ジョブをアプリの runtime イメージのコマンド違いで動かし、migrate イメージをやめた（Issue #326）
- 理由: daiki の「二つ image build push するの嫌だな。同じ image のコマンド違いで migrate だけ実行にしたい」。
- 根拠: runtime イメージ（standalone）を docker build して中を見た（この環境では corepack の取得が TLS プロキシで失敗するので、CA を build secret で渡す検証用の Dockerfile を scratchpad に作り `--network host` で build。2026-09-30 と同じ方法）。`/app/node_modules/.pnpm` に pg はあるが drizzle-orm は無い（Turbopack がサーバのチャンクに束ねる）。そこで入口 `apps/backend/shared/drizzle/migrate.ts` を esbuild 0.28.2（latest、2026-08-08 公開。lockfile に既にあった版）で `dist/migrate/migrate.mjs` に束ねた。実測: (1) drizzle-kit migrate で当てた DB に束ねたファイルを実行して記録 4 件のまま・exit 0、(2) 空の DB に当てて 3 表と記録 4 件、(3) 新しい runtime イメージで `node migrate/migrate.mjs`（USER node）が空の DB に当てて exit 0・再実行も exit 0・存在しない DB で exit 1・環境変数なしで env.ts のエラー、CMD は server.js のまま。イメージは圧縮 93.7MB → 93.9MB。
- 判断: コマンドは Terraform ではなく deploy.yml の `gcloud run jobs update --image ... --command node --args migrate/migrate.mjs` でイメージと組で入れ替え、Terraform は command / args を ignore_changes（初回の apply の hello イメージに node が無く、apply とデプロイの順序に依らないため）。`pnpm db:migrate` も束ねたファイルを実行するようにし、CI が毎回ジョブと同じファイルを通す。drizzle-kit は generate だけに使い、drizzle.config.ts の dbCredentials と env の import を消した。採用しなかった案（runtime に drizzle-kit を入れる・型の除去で .ts を直接動かす・pnpm deploy）は ADR `docs/adr/tech-stack/20261002-migrate-job-same-runtime-image.md`。
- 機械化: 縛れる（`migration.postgres.test.ts` が当てる・再実行で何もしない・失敗でもプールを閉じるを固定、CI の `pnpm db:migrate` が束ねたファイルを毎回実行、`rule-tests/test-support.test.ts` の deploy-verifies-images が runtime の検査のステップだけを求める）。runtime イメージの中の `migrate/` の有無は CI ではイメージを作らないので縛れない（main へのデプロイの Run migrations で止まる）
