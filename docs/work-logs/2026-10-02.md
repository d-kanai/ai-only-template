## Repository の repairHistory（repair on read / write）を消した（Issue #260）
- 理由: daiki「function repairHistory これ無くしたい。古い下位互換用の処理とかは不要」。本番環境が無く、旧リビジョンが書いた行を読むことが無い。
- 根拠: `repairHistory`（`todo-repository.postgres.ts`）と `Todo.reconstruct(values, stored?)` の `stored` は、デプロイの切替から backfill までの間に旧アプリが書いた Todo（履歴が無い・食い違う）を補うためのもの（ADR `workflow/20261001-backfill-after-traffic-switch.md`・Issue #194・#237、コメントで確認）。呼び出し元は `toTodo` だけ（`grep -rn repairHistory`）。履歴が無い・食い違う行が 500 になるテストを先に足して 3 件の失敗を確かめ、削除後に `pnpm lint`・`pnpm typecheck`・`pnpm test`（3549 件、カバレッジ 100%）が通ることを確認した。
- 判断: backfill の仕組み（`db:backfill`・deploy.yml の Run backfill・`backfill/0001_*.sql`）は依頼の対象外として残し、SQL の `FOR UPDATE OF` / `ON CONFLICT` は守りとして残した（コメントで経緯を記す）。消すかは daiki に確認する。ADR は不変なので新しい ADR `workflow/20261002-drop-repair-on-read-without-production.md` を足し、旧 ADR を「置き換え」にした（状態の値に「一部の置き換え」が無いため。新しい ADR の決定で backfill の方針を引き継ぐと明記）。
- 機械化: 縛れる（履歴が無い・食い違う行が 500 になることを `todo-repository.postgres.test.ts` で固定した）
