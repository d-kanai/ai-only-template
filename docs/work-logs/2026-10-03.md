## Issue テンプレート（Issue forms）を type ラベルごとに 5 つ置いた（Issue #113）
- 理由: daiki が棚卸しの Issue #113 の実施を選んだ。`.github/` には PR テンプレートしか無く、Issue の形（目的 / 内容 / 完了条件）は運用で揃えていた。
- 根拠: 比較検討（1 つの共通テンプレート vs type ごとの 5 つ）: Issue forms の `labels` はテンプレートごとの固定値で、ドロップダウンの値からラベルを付ける仕組みは公式の構文（https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms ）に無い。「選ぶだけで type ラベルが 1 つ付く」完了条件を満たすため 5 つにした。共通 1 つは、ラベルを手で付ける運用が残るので採らなかった。`config.yml` の `blank_issues_enabled: false` で空の Issue を止める（API で作る Issue はテンプレートを通らないので、スキル pr-flow の手順 1 に同じ見出し `### 目的` / `### 内容` / `### 完了条件` / `### 前提` で書くことを足した）。5 つのラベルが repo にあることは REST の labels の一覧で確認。GitHub の「New issue」の画面でフォームとして表示されるかは、マージ後に確かめる（未確認）。
- 機械化: 縛れる（`rule-tests/issue-template.test.ts`。置くファイル・labels・項目の順と必須・空の Issue の禁止。API で作る Issue の見出しは GitHub 上のデータなので縛れない）

## ヘルスチェック GET /api/health を作り、停止は Next.js の標準処理に任せると決めた（Issue #107）
- 理由: デプロイ先や外の監視が生死を判定する口が無く、終了時にプールを閉じる経路も無かった（Issue #107）。
- 根拠: Next.js 16.3.6 の `node_modules/next/dist/server/lib/start-server.js` は `NEXT_MANUAL_SIG_HANDLE` が無ければ SIGTERM / SIGINT で `server.close()`（新しい接続を受けず処理中を待つ）→ `nextServer.close()` → `process.exit(143)`。standalone の `server.js`（`next build --webpack` の最小アプリをスクラッチで作成）で実測: 3 秒のリクエストの途中で SIGTERM → そのリクエストは 200（3.02 秒）、SIGTERM の 0.3 秒後の新しい接続は拒否（curl の exit 7）、終了コード 143。standalone の server.js は `require('next/dist/server/lib/start-server')` の `startServer` を使う（生成物を grep）。Cloud Run は SIGTERM から 10 秒後に止め、処理中のリクエストは完了を待ち、新しいリクエストはほかのインスタンスへ送る（https://docs.cloud.google.com/run/docs/container-contract ）。
- 判断: liveness / readiness は分けず DB まで見る 1 本（今は Cloud Run にプローブが無い）。proxy の matcher からは除外しない。SIGTERM で `AppDatabase.close()` を呼ぶ案は、終了前に後から接続を取る処理中のリクエストを 500 にしうるので採らない（Next.js に「処理中が終わった後」の口が無い）。ADR `docs/adr/architecture/20261003-health-check-and-shutdown.md`。
- 実装の事実: logger は application から使えない（`SHARED_MODULES_BY_LAYER`）ので、ログは presentation から出す。drizzle-orm 0.45.3 は失敗を `DrizzleQueryError` で包み、logger が query を持つ例外の message を `***` にするので、infra で cause を取り出して投げ直す（worker が実測）。request を使わない GET でも `pnpm build` の出力は `ƒ /api/health`（prerender されない）。
- 未確認: Cloud Run 上での `/api/health` の応答（デプロイ後に確かめる）。ADR `20260930-log-format-cloud-logging-otel.md` の event.name の一覧に `health_check_failed` が無い（ADR は不変なので直さない。一覧の正は `apps/shared/log-event.ts`）。
- 機械化: 縛れる部分は縛った（API 網羅率・API 仕様の対・プールが 1 つの検査に health が自動で入る）。停止の振る舞い（Next.js 任せ）は字句で縛れない（ADR に理由を残す）
