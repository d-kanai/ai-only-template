## architecture の ELOOP のテストが CI でときどき落ちる原因を実測で確かめ、列挙を直した（Issue #346）
- 理由: PR #345 の CI で「除外の外に置いた循環する symlink … ELOOP の例外で止まる」が `syscall: 'scandir'`（期待は `stat`）で落ちた。テストのコードは直前の緑の実行と同じ。
- 根拠: Linux の `fs/namei.c`（torvalds/linux master を curl で取得）で、たどった symlink の数 `total_link_count` は `__set_nameidata` で 1 回だけ初期化され、`filename_lookup`（stat）と `do_filp_open`（readdir の open）の RCU → ref-walk の再試行（`-ECHILD`）で引き継がれる。`follow_dotdot_rcu` は `mount_lock` の seq が変わると `-ECHILD` を返す。実測（Node 24.21.0、ext4）: 何もしないと 2000 回中 stat 1996・scandir 4。`unshare -m` で tmpfs の mount / umount を並行で繰り返すと 直す前の列挙は stat 1013・scandir 718・例外なし 269（`existsSync` が ELOOP を false にして空を返す）、直した後は stat 1376・scandir 624・例外なし 0。テストも main のままでは 5 回中 3 回落ち、直した後は 5 回とも通った。
- 判断: テストは `code: "ELOOP"` だけを比べる（syscall と段数は kernel の再試行で決まらない）。`walkFiles` の有無の確かめを `existsSync` から `statSync(..., { throwIfNoEntry: false })` に変え、ELOOP を「無い」として黙って途中までの一覧を返す穴を塞いだ。その穴を決定的に固定するテスト（apps/backend 自体を自己循環の symlink にする）を足した。`listDirectFiles` の `existsSync` は再帰せず symlink もたどらないので今回は変えない。
- 機械化: 縛れる（`rule-tests/architecture.test.ts` の「ファイルの列挙」の 2 つのテスト）
