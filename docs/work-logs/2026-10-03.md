# 2026-10-03

## pnpm audit を CI に入れた（Issue #112）
- 理由: daiki が基盤整備の候補から #112 を選んだ（「1-6やって」）。CI は依存の既知の脆弱性とコードの脆弱性のパターンを検査していなかった。
- 根拠: `pnpm audit`（pnpm 12.7.0、2026-10-03 実測）は moderate 4 件（GHSA-67mh-4wv8-2f99 / GHSA-q8mj-m7cp-5q26 / GHSA-x5fp-wj9c-mxmx / GHSA-4mjr-xmp4-gh2g。qs など Stryker の推移的依存）、high 以上は 0 件。`pnpm audit --audit-level high` は終了コード 0、`--audit-level moderate` は 1。`pnpm-workspace.yaml` に `auditConfig.ignoreGhsas: [GHSA-x5fp-wj9c-mxmx]` を一時的に足すと「3 vulnerabilities found / 1 ignored」になった（確認後に戻した）。`minimumReleaseAgeExclude` は pnpm 本体（`strings`）に設定名があることだけを確かめた（効くかは未確認）。
- reviewer の指摘で直した: 判定の行読みが、`run:` の次の行に書いた `|| true`（YAML では値の続き）を見逃していた（🔴）。あわせて `with:` / `env:` の下のキーの取り違え・job の `if`・`paths` / `paths-ignore` も拒否にした（🟡）。Codex の P2 で、job の `continue-on-error` と、`steps:` の外（matrix の include など）の `run:` も拒否にした。
- 判断: audit は ci ジョブ（required）の中で high 以上を失敗にする（ADR `docs/adr/quality/20261003-pnpm-audit-in-ci.md`。採用しなかった案も ADR）。
- 未確認: repo の Secret scanning / push protection の状態（セッションの `GH_TOKEN` では `security_and_analysis` が返らない）。daiki に Settings → Code security で見てもらう。
- 機械化: 縛れる（`rule-tests/github-actions.test.ts` の `auditsDependencies`。ci ジョブの audit の形とトリガーを検査する）。リポジトリの設定（secret scanning）は縛れない（セッションから読めない）。

## CodeQL は入れないことにした（daiki の判断）
- 理由: 一度 advanced setup の `codeql.yml` を書いたが、daiki が「本番は private にするから有料ならいらない。lint などの静的解析で十分では」と判断した。
- 根拠: GitHub Docs の about-code-scanning（`content/code-security/code-scanning/introduction-to-code-scanning/about-code-scanning.md`）で、code scanning は public の repo と、Team / Enterprise の組織で GitHub Code Security を有効にした repo だけと確認（個人の private repo は対象外）。
- 機械化: 対象外（判断のみ。入れないことを縛る規則は作らない）
