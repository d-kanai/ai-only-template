## 調査結果: backend のエラーメッセージの翻訳を世の中はどう管理しているか（researcher、一次情報）
- パターン A（サーバが翻訳した文言だけ）: Laravel の 422（`errors: { field: [文言] }`、コード無し）、Rails の `full_messages`。Accept-Language を自動で読む記述は両方の公式に無い
- パターン B（コード + params、クライアントが翻訳）: Slack Web API（`{ ok: false, error: "code" }` だけ）、Zod（公式「code is the key, and the issue's other properties are the interpolation values」）、vee-validate の i18n、Rails の `errors.details`（`{ error: :too_short, count: 3 }`）
- パターン C1（コード + 開発者向けの英語 message。翻訳しない）が大手 API で最多: Google AIP-193（`Status.message` は developer-facing・英語、機械可読は `ErrorInfo{reason, domain, metadata}`、文言に埋め込む値は metadata に）、Microsoft Graph（message は「aid to developers, should not be exposed to end users」）、Azure、GitHub REST（`errors[]{resource, field, code}`）、Stripe（`type / code / decline_code / param / message`）、Twilio、AWS、Kubernetes（`reason` は machine-readable、`details.causes`）、Shopify（`userErrors{code, field, message}`）
- パターン C2（コード + サーバが翻訳した message）: Google の `LocalizedMessage`（任意）、Spring の `ProblemDetail` + `MessageSource` + `LocaleResolver`、Django / DRF（`code` と `params` を推奨、`LocaleMiddleware` は URL → cookie → Accept-Language の順）、nestjs-i18n、ASP.NET Core（クエリ → cookie → Accept-Language）
