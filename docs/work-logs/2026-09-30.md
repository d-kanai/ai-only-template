## 質問への回答: presentation のエラーハンドリングは各 API の try / catch だけか、共通化できるか
- 根拠（コードの確認）: `apps/backend/features/todo/presentation/*.api.ts` 5 本すべてが `handle` の中で `try { ... } catch (error) { return toProblemResponse(error, request); }` を書いている。変換の規則（DomainError → 400 / 404、InvalidRequestError → 400、それ以外 → logger.error + 500 固定文言）は `shared/presentation/problem.ts` の `toProblemResponse` の 1 か所に集まっている。Next の Route Handler には共通の catch の仕組みが無い（Proxy は handler の例外を捕まえられず、未処理の例外は Next の 500 になる。`instrumentation` の `onRequestError` は記録だけで応答は変えられない）。

## 質問への回答: presentation の検証と domain の検証は重なってよいか（presentation ⊂ domain の関係）
- ユーザーの考え: 役割をあえて分けるのは難しいので両方に被ってよい（長さ・必須は両方にあってよい）。domain はそれに加えてドメイン固有の規則（組み合わせ、配列は 3 つまで など）を持つ。つまり presentation < domain。
- 現状（コードの確認）: presentation は形だけ（`requestBodySchema` で型と未知の項目。`update-todo.api.ts` は `title: z.string().optional()`）、domain（`todo.ts`）が trim 後 1〜100 文字を 1 か所で持つ（Issue #88 / #94）。どちらの違反も `toProblemResponse` で同じ 400 の problem+json（key 付き）になるので、クライアントから見た結果は同じ。違いは presentation の zod だけが `errors[]`（項目ごとの pointer 付き）を複数件返せること。domain は最初の違反で throw する。
- 回答: presentation ⊆ domain には賛成。条件 3 つ: (1) domain は常に完全（presentation が何を検査しても、domain 単体で全不変条件を守る。admin（#135）やジョブなど別の入口が増えても壊れない）、(2) presentation は domain より厳しくしない（domain が通す値を presentation で落とすと domain の規則が到達不能になり「テスト = 仕様」が domain で読めなくなる）、(3) 数値（100 文字など）は 2 か所に書かず domain の定数を presentation が参照する。ただし今の規則は「presentation から自 feature の domain は `import type` のみ」（`backend.md`）なので、定数の参照を許す緩和が要る。
- 未実施: 規則の変更は Issue にしていない（ユーザーの判断待ち）。

## 質問への回答: そもそも presentation の検証は要るか
- 根拠（コードの確認）: `json-body.ts` の presentation の検証が出すキーは `request.body.notJson` / `notObject` / `unknownKeys` と `request.field.notString` / `notBoolean`。これは「HTTP の本文を、command が受け取る型付きの入力に変える」段階でしか判定できない（JSON として読めるか、オブジェクトか、未知の項目が無いか、項目の型）。domain の `todo.ts` は zod で `title` が文字列で trim 後 1〜100 文字かを見るので、型違いは domain でも `todo.title.invalid` として止まるが、未知の項目（`{ complete: true }` の打ち間違い）は command の引数に無いので domain には届かず黙って無視される。`CreateTodoRequest` などの型もこのスキーマから導出して画面が使う。
- 回答: presentation の検証は「形（JSON / オブジェクト / 未知の項目 / 項目の型）」の分は要る（HTTP 境界の責務で domain には代替できない）。長さ・必須などの意味の検査は既定では domain だけに置き、項目ごとの `errors[]` をまとめて返したい API だけ presentation に重ねる（前項の条件 3 つ）。つまり「presentation は最小限 + 必要なら重ねる」が推奨。

## 質問への回答: partial update（状態遷移の差分だけを SQL にする dirty tracking）をどうするか

- 選択肢: (A) 全列 upsert のまま（現状。列 2 つで差分の効果が無い。欠点は同時更新で他方の列を巻き戻す lost update。backend.md に記載済み）/ (B) Entity が変更した項目を持つ（不変のまま `changed: Set<"title"|"completed">` を遷移メソッドで積み、save がその列だけ UPDATE。永続化の都合が domain に入る）/ (C) Repository が読んだ行のスナップショットと比べて差分だけ書く（ORM の dirty tracking の形。Repository はモジュール読み込み時に 1 つ作って全リクエストで共有しているので、リクエスト単位の identity map が要る）/ (D) 遷移ごとの Repository メソッド（`rename(id, title)` = `UPDATE ... SET title`。差分は明示、隠れた状態が無い）/ (E) version 列の楽観ロック（`UPDATE ... WHERE id AND version` → 0 行なら 409）。差分ではなく lost update を止める。
- 推奨: 今は (A) のまま。差分が要るのは「同時に別の列を変えるのを両立させたい」「列が多く書き込みが重い」のときで、そのときは (D)（明示）か (E)（正しさ）を先に検討し、隠れた状態を持つ (B)(C) は採らない。決めるときは Issue に書く。
- 根拠: 現状のコード（`todo-repository.postgres.ts` の save、`update-todo.command.ts`）、backend.md の READ COMMITTED の記述。drizzle に変更追跡が無いことは公式ドキュメント（クエリビルダ / relational queries のみ）に基づく理解で、版ごとの確認は未実施。

## 質問への回答: `#origin` の `#` は何か
- 回答: ECMAScript のプライベートフィールド（`#name`。ES2022 で標準化）。TypeScript の `private` は型の上だけの制限で、実行時は普通の own property として列挙・直列化・`toEqual` の比較に入る。`#` は実行時にも外から見えず、`Object.keys` / `JSON.stringify` / Vitest の `toEqual` に混ざらない。#165 で origin を持たせるときに、公開や TS の `private` だと「create した Todo と読み込んだ Todo が toEqual で等しくない」になって既存テストが壊れるため、worker が `#` を選んだ（`todo.ts:97` の WHY）。リポジトリで `#` フィールドを使うのはここが初めて（`grep`）。
- 補足: `tsconfig.json` の `target` は ES2017 で、tsc はこの target では `#` を WeakMap に落として出力する。ただしこのリポジトリの tsc は型チェックだけ（noEmit）で、実行コードは Next（SWC / Turbopack）が作るので、実際の出力形は未確認。挙動はテスト（列挙されない・toEqual で無視される）で固定している。

## 質問への回答: migrate はなぜ別イメージか（drizzle だけか）、デプロイは GitHub Actions → Cloud Run でよいか
- 事実（Dockerfile）: Dockerfile は 1 つで `--target` で 2 つを作り分ける。`deps`（Node + pnpm + lockfile どおりの依存。devDependencies を含む）→ `build`（next build）→ `runtime`（素の Node slim に `.next/standalone` だけ）。`migrate` は `deps` からそのまま作り `CMD pnpm db:migrate`（drizzle-kit migrate）。つまり migrate は「drizzle だけ」ではなく、リポジトリのソースと全依存（devDependencies 込み）を持つ約 385MB のイメージで、runtime とは別物（deps の層はビルドキャッシュで共有）。WHY 別にする: drizzle-kit は devDependency で、マイグレーションの SQL と `@repo/shared/env` のソースが要り、standalone には入らない。runtime に drizzle-kit を入れると本番のサービスに要らないものが載る。
- 小さくする案（今はやらない）: (a) migrate 専用の install（`pnpm install --filter @repo/backend` + drizzle の設定と SQL だけをコピー）、(b) drizzle-orm の `migrate()` を呼ぶ小さな `migrate.js` を書いて runtime と同じ standalone 相当に載せる（drizzle-kit 不要）。ジョブは短時間しか動かず Cloud Run のジョブは実行時間課金なので、イメージの大きさは費用にほぼ効かない（Artifact Registry の保存は古いイメージの削除で抑えている）。

## 質問への回答: CHECK 制約の張り直しのリスク（遅い・ロック）
- 根拠（PostgreSQL 公式 ALTER TABLE、2026-09-30 に確認 https://www.postgresql.org/docs/current/sql-altertable.html ）: `ADD table_constraint` は既定で ACCESS EXCLUSIVE ロックを取り、CHECK の追加は既存の全行を走査して検証する（表の書き換えは不要）。`NOT VALID` を付けると走査を飛ばし、以後の INSERT / UPDATE だけに適用される。`VALIDATE CONSTRAINT` は SHARE UPDATE EXCLUSIVE で、同時の更新を締め出さずに既存行だけを検査する。`DROP CONSTRAINT` のロックはこのページに明記なし（未確認。一般に短い ACCESS EXCLUSIVE）。
- 回答: リスクは「追加時の全行走査の間、ACCESS EXCLUSIVE で読み書きが止まる」こと。`change_logs` は増え続ける表なので行数に比例して伸びる。回避は 2 段階（`ADD CONSTRAINT ... NOT VALID` → `VALIDATE CONSTRAINT`）。Issue #198 の初回は表がほぼ空なので 1 文でよいが、SQL には将来の張り直し向けに 2 段階の書き方をコメントで残す。
- 機械化: 対象外（質問への回答）。大きい表への CHECK の追加を `NOT VALID` 無しで書いたら止める検査は、表の大きさが SQL から分からないので機械では見ない。
