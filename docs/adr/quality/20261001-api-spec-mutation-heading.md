# 書き込みの API 仕様は、メインの変更（作成 / 更新 / 削除）とレスポンスを別の Scenario に分け、見出しを一覧の順に並べる

- 日付: 2026-10-01
- 状態: 採用
- 関連: Issue #249 / `.claude/rules/testing.md`（「API 仕様テスト（api-specs）」） / `rule-tests/api-spec.test.ts` / quality/20260930-api-spec-in-feature.md

## 背景
API 仕様の見出しは quality/20260930-api-spec-in-feature.md で、書き込みの API は レスポンス / 記録 / 副作用 / 異常系と決めた。その結果、create の「レスポンス」に「未完了の Todo が作られて返る」「タイトルの前後の空白は除かれる」「100 文字まで作れる」が並び、作られる Todo の規則と返る内容が 1 つの見出しに混ざった。rename・change-todo-completion・delete でも、対象の Todo 自身の変化が「レスポンス」と「記録」に散っていた。ユーザーが、メインの変更とレスポンスを分け、書き込みの API すべてで揃えるよう求めた（2026-10-01）。

## 決定
- 見出しの一覧に、メインの変更の見出し `作成` / `更新` / `削除` を足す。書き込みの API の見出しは「作成・更新・削除のどれか 1 つ / レスポンス / 記録 / 副作用 / 異常系」（該当の無い見出しは省く）。
- 振り分け: メインの変更 = 対象の Todo 自身が操作の後どうなるか（規則を含む）、レスポンス = 返る内容、記録 = 対象の Todo のほかに残るもの（完了の履歴）、副作用 = 通知など。
- 見出しは一覧の順（作成 / 更新 / 削除 / レスポンス / ソート / 検索 / 記録 / 副作用 / 異常系）に並べる。
- メインの変更の見出しは 1 つまでで、記録か副作用があれば 1 つ要る。順と数は `rule-tests/api-spec.test.ts` の `api-spec-scenario-order` / `api-spec-write-heading` で止める。
- quality/20260930-api-spec-in-feature.md のほかの決定（置き場所・`*` の step・業務の言葉・実 DB）は変えない（その ADR の「見直す条件」に書いた、見出しの一覧に観点を足す変更にあたる）。

## 理由
- 「作られる」と「返る」を別の見出しにすると、読む人がどちらの振る舞いの仕様かを見出しで読み分けられる。メインの変更の step は保存された行を、レスポンスの step は応答を見るので、確かめる対象も見出しと揃う。
- 見出しの名前を操作（作成 / 更新 / 削除）にすると、どの書き込みの API でもメインの変更の場所が先頭の 1 つに決まる。
- 順と数を検査にすると、AI が書いても形が崩れない（CLAUDE.md の 7）。

## 採用しなかった案
- メインの変更の見出しを API ごとの名前（名前の変更・完了の切り替えなど）にする: 固定の一覧で検査できず、API ごとに見出しが変わって拾い読みしにくい。
- メインの変更の見出しを 1 つの語（`変更`）にする: ユーザーが create を「作成」と呼んだのと合わず、作成・削除まで「変更」と呼ぶのは業務の言葉として不自然。
- 「記録」をメインの変更の見出しに改名する: 完了の履歴のような対象の Todo のほかに残るものの置き場所が無くなる。

## 影響
- 良い点: 書き込みの 4 つの API で、メインの変更 → レスポンス → 記録 → 副作用 → 異常系の同じ順で読める。
- 悪い点: メインの変更と記録の境目（対象の Todo 自身か、ほかに残るものか）は検査できず、書く人と reviewer が判断する。
- 見直す条件: 記録も副作用も無い書き込みの API ができたら、書き込みの API の判定を見出しではなく api ファイル（HTTP メソッドなど）で行うか検討する。
