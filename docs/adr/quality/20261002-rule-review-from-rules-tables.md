# コード・設計ルールのレビューは rules の表の「レビュー」の行を観点にし、検出 → 1 件ずつ検証 → 重大度で報告するスキルで行う

- 日付: 2026-10-02
- 状態: 採用
- 関連: Issue #330 / Issue #322 / `REVIEW.md` / `.claude/skills/rule-review/SKILL.md` / `docs/adr/workflow/20261002-code-rules-as-tables.md`

## 背景
daiki が、コーディング・設計ルールをレビューする skill を求めた（2026-10-02）。Issue #322 で `.claude/rules/code/*.md` を「カテゴリ | WHAT | WHY | 強制」の表にし、機械で止めていない規範は強制の列が `レビュー` になった（約 165 行）。Anthropic の一次情報（Claude Code の code-review プラグイン `plugins/code-review/commands/code-review.md`、Code Review の docs https://code.claude.com/docs/en/code-review 、プロンプトのガイド）は次を勧めている: linter・CI が見るものはレビューしない、検出と検証を分けて誤検知を落とす、ルール違反は文を引用できるときだけ指摘する、検出の段で「重大なものだけ」と絞ると見逃しが増えるので全部出させて別段で絞る、レビュー専用の指示は REVIEW.md に短く書く。

## 決定
- 観点は rules の表の `レビュー` の行そのもの（`grep -n '| レビュー |$'`）。差分のファイルに一致する `paths` を持つ rules のファイルだけを使う。観点を別ファイルに写さない。
- 基準（対象外・証拠・重大度 🔴 / 🟡 / 🟣・nit の上限・再レビュー）はリポジトリ直下の `REVIEW.md` に書く。
- 手順はスキル `rule-review`: 検出（rules のファイルごとに reviewer、全部出す）→ 検証（指摘 1 件ごとに別の reviewer）→ 報告。
- スキルを変えたら `evals/` の patch（違反あり 2・違反なし 1）で通して期待と比べる。

## 理由
- 観点を rules の行に置けば、規範・WHY・強制の手段が 1 か所で、行を直せばレビューも変わる。機械で止まる行を外すので、レビューが CI と同じことを二重に見ない。
- `REVIEW.md` は Code Review（GitHub アプリ）が読むファイル名なので、後で入れたときも同じ基準になる。
- 検出と検証を分けるのは公式の 2 つの実装（code-review プラグイン・security-review）と同じで、検証を別のコンテキストにすると、指摘を出したエージェントの思い込みを引き継がない。

## 採用しなかった案
- REVIEW.md に観点の一覧（約 55 の問い）を書く: rules と二重管理になり、ずれる。
- `.claude/rules/code` を丸ごとレビューのエージェントに渡す: 約 10 万字で、機械で止まる規範と説明に、レビューで見る規範が埋もれる。
- 検出の段で確信の高いものだけを出させる: 公式のプロンプトのガイドが recall の低下を挙げている。

## 影響
- 良い点: rules に `レビュー` の行を足すだけで観点が増える。機械化した行は強制の列が変わり、自動でレビューから外れる。
- 悪い点: 指摘ごとに検証のエージェントを起動するので、指摘が多い差分では消費が増える。
- 見直す条件: 評価で見逃しや誤検知が続く、または Code Review（GitHub アプリ）を入れて CI でレビューするとき。
