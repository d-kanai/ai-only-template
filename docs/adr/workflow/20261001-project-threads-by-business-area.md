# 1 Issue = 1 セッションをやめ、Claude Code Projects のスレッドは業務の単位で分け、開発は 1 つのスレッドで続ける

- 日付: 2026-10-01
- 状態: 採用
- 関連: Issue #242 / `.claude/general/orchestration.md` / `.claude/general/workflow.md` / スキル `pr-flow`

## 背景
ADR `workflow/20260929-save-usage-limit.md` で、消費を抑えるために「1 Issue = 1 PR = 1 セッション（`/clear`）」にしていた。その後、開発を Claude Code Projects で進めるようになった。Projects では、スレッドごとに独立した Claude Code セッションがレポを clone して起動する。CLAUDE.md と `.claude/agents/` はスレッドごとに読み込まれ、スレッドの会話（コンテキスト）は他のスレッドに自動では届かない（2026-10-01 の work-logs）。ユーザーは、1 人のオーケストレータにタスクを続けて依頼し、依存や順番を調整してもらう形で開発している。

## 決定
- 置き換える決定: ADR `workflow/20260929-save-usage-limit.md` の「1 Issue = 1 PR = 1 セッション（`/clear`）」のうち、「1 セッション」の部分。1 Issue = 1 PR と、その ADR のほかの決定（wake の削減・軽い worker など）は引き継ぐので、その ADR は「採用」のまま。
- Claude Code Projects のスレッドは、業務の単位（開発・マーケティング・経理など）で分ける。
- 開発は同じスレッドで続け、そのスレッドの Claude がオーケストレータとして、Issue をまたいで依存・順番を調整し、サブエージェントに依頼する。

## 理由
- スレッドのコンテキストは共有されないので、開発をスレッドに分けると、オーケストレータによる依存・順番の調整が切れる。
- プロジェクトの調整役（スレッドを立てる Claude）の役割は依頼の振り分けで、スレッドをまたいだ細かい調整の代わりにはならない（仕組みの説明から判断した。実際には試していない）。
- ユーザーの判断「1 Issue 1 session ルール廃止。開発系は同じスレッド。マーケティング、経理、開発などの粒度でスレッドは分ける」（2026-10-01）。

## 採用しなかった案
- Issue ごとにスレッドを立てる（1 Issue = 1 セッションをそのまま Projects に当てはめる）: Issue 同士の依存を調整する役がいなくなる。
- 開発のスレッドでも、関連の薄い大きな機能に移るときは新しいスレッドに切り替える（スレッドで提案した）: ユーザーの判断で採らなかった。

## 影響
- 良い点: 依存のある開発タスクを、1 人のオーケストレータが通して調整できる。
- 悪い点: 開発のスレッドが長くなり、毎ターン送るコンテキストが増えて消費が膨らむ（ADR `workflow/20260929-save-usage-limit.md` の理由）。コンテキストが圧縮（要約）されると、細部が失われることがある。
- 見直す条件: 消費が Usage limit に早く達するようになったとき。
