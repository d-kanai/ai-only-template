# .claude/rules/code の規則は「カテゴリ | WHAT | WHY | 強制」の表で書き、何が止めるかを行ごとに示す

- 日付: 2026-10-02
- 状態: 採用
- 関連: Issue #322 / `.claude/rules/code/` / `rule-tests/rules-table.test.ts`

## 背景
コード・設計ルールをレビューする skill（REVIEW.md）を作るにあたり、`.claude/rules/code/` の 4 ファイル（約 10.7 万字）を調べた。規範・WHY・経緯・検査器の限界・ファイルの一覧が 1 つの箇条書きに混ざり、どの規範が rule test などで機械的に止まり、どれがレビューでしか見られないかを読み取れなかった。Anthropic のレビューの指針（Claude Code の code-review プラグイン、Code Review の REVIEW.md）は、linter・CI が見るものをレビューから外し、レビュー専用の指示は短く具体的にすることを勧めている。

## 決定
- `.claude/rules/code/*.md` の本文を、見出しと `| カテゴリ | WHAT | WHY | 強制 |` の表（とコード例のコードブロック）だけで書く。1 行 = 1 規範（または 1 説明）。
- 「強制」の列は `レビュー`（機械で止めていない規範）/ `説明`（規範ではない）/ 止める検査への参照（`rule-tests/<名前>.test.ts` の `<規則名>`・`biome.json`・`pnpm typecheck` など）のどれか。一部だけ機械で止まる規範は、止まる行と限界の `レビュー` の行に分ける。
- 形と参照先の実在（パスと規則名）は `rule-tests/rules-table.test.ts` が検査する。
- 今回は圧縮しない（内容は削らない。ユーザー判断 2026-10-02「圧縮はしないでまず表にして」）。

## 理由
- 「強制」の列があれば、REVIEW.md に回す規範（`レビュー` の行）と、rule test に寄せる候補を表から拾える（ユーザー判断 2026-10-02「それなら ruletest に入っているか、review md もやりやすい」）。
- 参照先を rule test で確かめるので、規則名の変更・削除で文書が古くなると機械で止まる（CLAUDE.md の原則 7）。

## 採用しなかった案
- 箇条書きのまま、レビュー用の観点を別ファイルに抜き出す: rules と二重管理になり、どちらが正かずれる。
- 先に圧縮する: 何が機械で止まるかを分けないまま削ると、必要な規範と WHY を落としやすい。圧縮は表にした後で検討する。

## 影響
- 良い点: 規範ごとに理由と強制の手段が並び、レビューと機械化の対象を行で選べる。
- 悪い点: 表のセルは長くなり、生の Markdown では読みにくい。セルの中の `|` は `\|` と書く必要がある。
- 見直す条件: 表のままでは読み落としが増える、または quality / tooling の rules にも同じ形を広げるとき。
