# Claude Code Projects のスレッドは開発もタスクごとに分け、関連が深くコンテキストを引き継ぎたいときだけ同じスレッドで続ける

- 日付: 2026-10-01
- 状態: 採用
- 関連: Issue #245 / Issue #242 / PR #243 / `.claude/general/orchestration.md` / `.claude/general/workflow.md` / スキル `pr-flow`

## 背景
ADR `workflow/20261001-project-threads-by-business-area.md`（PR #243）では、スレッドは業務の単位で分け、開発は 1 つのスレッドで続けることにした。スレッドのコンテキストは共有されないので、1 人のオーケストレータに Issue をまたいで依存を調整させるためだった。マージの直後に、ユーザーがこれを見直した。

## 決定
- 開発もタスク（Issue）ごとに別スレッドにするのが基本。スレッドの Claude がオーケストレータになる。
- 内容が関連していて、同じスレッドでコンテキストを引き継いだほうがよいときだけ、既存のスレッドで続けてよい。
- 開発以外の業務（マーケティング・経理など）も別スレッドにする。
- スレッドをまたぐ依存は Issue に書く。
- 前の ADR の次の決定は引き継ぐ。
  - 1 Issue = 1 セッション（`/clear`）はやめる。
  - 指示ファイルの変更は専用の Issue にまとめ、ほかの Issue の作業の途中では変えない（区切りはセッションの最初ではなく Issue）。

## 理由
- ユーザーの判断「開発全てスレッドにまとめるはやめる。内容が関連していて、同じスレッドの方がコンテキスト的に良いと思ったらそうして良いけどそれ以外は別スレッド。マージとか見やすいから」（2026-10-01）。
- スレッドごとに PR とマージの経過が分かれるので、追いやすい。
- 関連する作業は同じスレッドにまとめられるので、依存の調整が要るところではコンテキストを保てる。

## 採用しなかった案
- 開発をすべて 1 つのスレッドで続ける（前の ADR）: PR とマージの経過が 1 つのスレッドに混ざって見にくい。
- Issue ごとに必ず新しいスレッドにする（1 Issue = 1 セッション）: 関連する作業でコンテキストを引き継げない。

## 影響
- 良い点: スレッドごとに PR とマージを追いやすい。1 つのスレッドが長くなりにくいので、消費も膨らみにくい。
- 悪い点: スレッドをまたぐ依存は、Issue を見ないとわからない。同じスレッドで続けるかどうかは、そのつど判断が要る。
- 見直す条件: スレッドをまたぐ依存の調整漏れが起きたとき。
