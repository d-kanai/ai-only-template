## Issue #88: zod で presentation の入力・domain の不変条件・完全コンストラクタの検証を統一した
- 根拠: worker（Opus）の実測。zod 4.6.5 の `.min / .max` は String#length なのでコードポイント数は `refine` で `Array.from` を数える。`z.uuid()` は RFC 9562 の形（版・variant の桁）だけを受け、Postgres の uuid 型より狭い（`randomUUID` は v4 なので実害なし）。`z.strictObject` 自身が出す issue は invalid_type と unrecognized_keys の 2 種類。`JSON.stringify` は `issues: undefined` を出力しない。オーケストレータの再実行: lint / typecheck / test 1567 件・カバレッジ 100% / build。mutation（19 ファイル）killed 242 / survived 0
- 判断（worker の提案を採用）: 未知の項目は拒否（`z.strictObject`。打ち間違いが「何も変えない」200 に化けない）。branded 型は使わない（restore は検証しないので brand を付けるには `as` で偽ることになる）。restore は parse しない（規則を厳しくしたときに既存データで 500 にしない。型は Drizzle のスキーマが保証）。`isUuid` は Repository の防御として残す。`InvalidRequestError` は `issues?` を持ち、`toErrorResponse` は zod を知らない。`readJsonObject` は `parseJsonBody(request, schema)` に統合。スキーマは関数の中で作る（Stryker の ignoreStatic）。issues が付くのは presentation の形の誤りだけ
- 挙動の変更: PUT は id を本文より先に確かめるので「uuid でない id + 不正な本文」は 400 → 404。frontend は変えていない（`issues?` は省略可能で `message` は残る）
- 採用しなかった案: valibot（関数合成の API で tree-shaking 向き。宣言の読みやすさで zod）、ArkType（型文字列の DSL。学習コストと issue の形の制御で zod）。性能・サイズは未実測（公式の説明に基づく）
